# ReelPuzzels

A TikTok-style vertical "reel" of brain puzzles. Solve one puzzle at a time, earn XP,
build streaks/combos, climb levels. Built from a Claude Design handoff (`Logic
games-handoff.zip`) — the mockup was visual reference only; all game logic here is real.

## Stack & commands

- **Vite + React 18 + TypeScript.** Builds to a self-contained static `/dist` (deployable to
  any static host — `vite.config.ts` sets `base: "./"` so it works under any subpath).
- `npm run dev` — dev server (http://localhost:5173).
- `npm run build` — `tsc --noEmit` typecheck + `vite build` → `/dist`.
- `npm run preview` — serve the production build.
- `npm run validate` — generator sanity harness (`scripts/validate.ts`): generates many
  puzzles per mode/tier and asserts each is well-formed + solvable by its win-predicate.
- `npm run smoke` — render smoke test (`scripts/smoke.tsx`): mounts every mode's component
  (solved + unsolved) via `react-dom/server` to catch render-time errors headlessly.
  (Both bundle with esbuild — a transitive Vite dep — and run on Node, no test runner.)

## How the app is wired

`src/main.tsx` → `src/App.tsx` is the screen router. Screens:
`onboarding | feed | single | menu | stats`. App owns theme + progress and passes them down.

- **Feed** (`src/screens/Feed.tsx`) — endless reel. Puzzles appended on demand (no fixed
  list, no progress dots). Difficulty **ramps** with `solvedCount` (`rampDifficulty` in the
  registry). Swipe / wheel / drag navigation ported from the mockup.
- **SingleGame** (`src/screens/SingleGame.tsx`) — practice one mode. Pick easy/medium/hard,
  play one puzzle at a time via a "Next puzzle" button. **No infinite scroll.**
- **Menu / Onboarding / Stats** — `src/screens/`. Stats are derived from real progress.

## Game modes are modular — this is the core extensibility point

Each mode is a self-contained folder under `src/games/<mode>/` that exports a
`GameModule` (see `src/types.ts`):

```ts
interface GameModule<D> {
  meta: GameMeta;                                   // id, skill label, styling
  generate(difficulty: Difficulty, rng: RNG): PuzzleInstance<D>;  // random puzzle
  Component: React.FC<PuzzleComponentProps<D>>;     // renders + drives the puzzle
}
```

**To add a new mode:** create `src/games/<mode>/` exporting a `GameModule`, then append it
to `MODES` in `src/games/registry.ts`. Nothing else changes — the feed, single-game,
menu, stats, and dispatch (`src/components/PuzzleBody.tsx`) all read from the registry.
(The menu thumbnail glyph for a mode is the one extra touch point: add an entry to
`MODE_ICO` in `src/screens/Menu.tsx`, else it falls back to "?".)

**Folder convention for the grid modes:** each splits into a pure `logic.ts` (the `Data`
type, `generate`, a `solved(...)` win-predicate, plus conflict/helper exports — **no
React**) and a `<Mode>.tsx` component that imports them. Keeping `logic.ts` React-free is
what lets `scripts/validate.ts` and `scripts/smoke.tsx` import the generators directly.
The same `solved(...)` predicate drives both the live win-check and the validator, so they
can't drift.

Current modes:
- `src/games/wordScramble/` — pick a word from a length bucket, shuffle letters, accept
  listed anagrams. Word pools in `words.ts`.
- `src/games/speedMath/` — 3×3 grid where each row obeys `c = a op b`; one cell blanked.
  `+` (easy), `*` (medium), mixed/larger (hard). Generator in `generate.ts`.
- `src/games/miniSudoku/` — 6×6 sudoku, 2×3 boxes. Full grid built by randomized
  backtracking, then clues dug out only while the solution stays **unique** (uniqueness
  solver in `logic.ts`). Tap a cell, tap 1–6. Live conflict highlighting.
- `src/games/queens/` — LinkedIn Queens. n×n (6/7/8 by tier), one coloured region per
  queen. **Guaranteed no-guess:** grow regions from the solution, then `repair` forces a
  *unique* solution by finding any alternate arrangement and moving one of its queen cells
  into an adjacent region (kills the alternate, keeps the true solution valid + regions
  contiguous); the board is then confirmed solvable by `solvableByLogic` — a deduction-only
  solver (singles + confinement + depth-2 contradiction elimination, no guessing). Random
  region maps are ~0% unique, which is why construction + repair is needed.
  **Interaction:** drag to cross off (✕) cells; a plain tap cycles empty → ✕ → ♛.
- `src/games/zip/` — draw one line through every cell, hitting numbered checkpoints in
  order. Path generated by the **backbite** algorithm (start from a snake path, fold an
  endpoint onto a random neighbour — provably stays Hamiltonian, never backtracks; a DFS
  search blew the stack on 7×7). **Interaction:** drag to draw the line (also tap-to-extend);
  the line is an **SVG overlay** (`.zip-line`) over a gapless grid; tap/drag back to retrace.
- `src/games/tango/` — 6×6 binary (☀/☾). Each row & column gets 3 of each, never 3 alike
  in a line, with `=`/`✕` pair clues. Full solution by backtracking; clues (revealed cells
  + relations, biased by tier) added until the solution is **unique**. Tap cycles
  empty → ☀ → ☾. `conflicts()` drives **live red highlighting** of any row/col that becomes
  impossible (4th of a symbol, 3-in-a-row, or a broken =/✕ clue).
- `src/games/patches/` — LinkedIn Patches (rectangle partition). Tile the whole grid with
  rectangles/squares; each shape holds exactly one clue cell that may reveal its size (cell
  count) and/or type (◻ square · ▯ tall · ▭ wide). Generated by guillotine `carve`, then a
  **top-left-anchored** solver (`countSolutions`) verifies uniqueness; clue fields are then
  hidden while uniqueness holds (more hidden = harder). **Interaction:** drag a rectangle
  around a clue to claim its cells (a rect must contain exactly one clue); tap a shape to
  reset it.

Drag modes share `src/games/pointer.ts` (`cellAtPoint` → maps a screen point to the cell
under it via `data-i`, for touch + mouse). Their grid carries `.drawgrid`
(`touch-action:none` + `stopPropagation` on touch) so a stroke draws instead of swiping the
reel.

Difficulty tiers: `easy | medium | hard`. Base XP per tier in `XP_BY_DIFFICULTY`
(`src/types.ts`): 100 / 150 / 220.

## Generation

`src/lib/rng.ts` — seedable RNG (mulberry32) with `int/pick/shuffle`, plus `uid()` for
instance ids. **Seedable on purpose**: a future server can hand the client a seed and both
sides produce identical puzzles.

## Scoring & timer (important behavior rules)

In `src/state/useProgress.ts` (`scoreSolve`, constants `DECAY=22`, `BONUS_FACTOR=0.6`,
`COMBO_STEP=15`):

- **The timer only ever counts UP.** There is no countdown anywhere (the mockup's live
  decaying speed-bonus meter was removed deliberately).
- The **speed bonus is computed but shown only AFTER solving**, in the solved tray
  (`src/components/PuzzleCard.tsx`, e.g. `+40 fast`). Never as a live meter during play.
- `gained = base xp + speedBonus + comboBonus`. Combo kicks in at streak ≥ 2.

## Progress store — built to move server-side

All progress goes through the async `ProgressStore` interface (`src/store/ProgressStore.ts`):

```ts
interface ProgressStore { load(): Promise<Progress>; save(p: Progress): Promise<void>; }
```

- Current impl: `LocalStorageStore` (key `rp_progress`).
- `src/store/index.ts` exports a single `store` instance — **the one line to change** to go
  server-side (swap for an `HttpProgressStore`). No call site changes, because everything
  consumes the interface via the `useProgress` hook.
- Theme (`rp_theme`) is a UI preference, persisted separately in `src/state/useTheme.ts`.

`Progress` = `{ xp, streak, bestStreak, solvedCount, timeSum, skills }`. `skills` is keyed
by mode id (solve counts), driving the Stats "skill power" bars.

## Styling

Ported from the design handoff, split into:
- `src/styles/tokens.css` — design tokens + both themes (`.stage[data-theme="neon|calm"]`),
  verbatim so colors/fonts match the mockup.
- `src/styles/app.css` — layout + components. The live speed meter was pruned (out of
  scope). The five grid modes share a `.board` / `.bgrid` / `.bc` scaffold near the bottom
  of the file, with per-mode rules under `.sudoku` / `.queens` / `.zip` / `.tango` /
  `.patches`. Boards size off `min(86vw, 300px)` (shrinks via `max-height` queries); the
  column count is the only inline style on `.bgrid`. Region colours (queens/patches) are
  inline, not tokens.

Font: Space Grotesk via `<link>` in `index.html`.

## Status / scope notes

- Seven modes implemented: **Word Scramble, Speed Math, Mini Sudoku, Queens, Zip, Tango,
  Patches**. The mockup's pattern / spatial / memory modes were never built (different
  mechanics).
- Progress is **local only** for now; the store is structured for a server backend later.
- Generators sanity-checked via `npm run validate` (2250 puzzles, all tiers): each
  generated puzzle's stored `solution` passes that mode's `solved(...)` predicate, and
  structural invariants hold — sudoku/tango/patches uniqueness, **queens logic-solvability**
  (`solvableByLogic`), queens region count, zip full coverage + checkpoint order, patches
  clue ownership. `npm run smoke` additionally mounts every component headlessly.
- The live pointer/drag → `onSolve` loop was verified **by hand in a real browser** (via the
  Chrome MCP): Queens drag-cross-off + tap-to-queen, Zip drag-draw + SVG line, Tango
  impossible-move highlight, and a full Patches rectangle-drag solve (→ celebration + XP
  tray), all with zero console errors. There's still **no automated** DOM test — drag uses
  `document.elementFromPoint`, which jsdom can't render; a Playwright test would be the way
  to lock it in.
